## 6. Apply MedEqualQA + MedFuzz perturbations to the MCQ anchor set

**Track:** Robustness · **Priority:** medium · **From spec:** `mamabench.md` (Safety set), `IMPLEMENTATION_PLAN.md` Step 9

MedEqualQA produces equity-perturbations; MedFuzz produces adversarial
paraphrases. Both apply to existing MCQ items (the "anchor set"). The
output is paired (original_id, perturbed_question, perturbed_choices, …)
that lets downstream scorers compute robustness-under-perturbation.

**To do:**
- Identify the MCQ anchor subset (probably a sampled slice of MedMCQA +
  MedQA-USMLE + AfriMed-MCQ).
- Apply or import MedEqualQA equity perturbations.
- Apply or import MedFuzz adversarial paraphrases (the eval plan
  explicitly mentions this for the contamination-adjusted score —
  `mamai-quality-evaluation.md` §5 reporting notes).
- Schema delta: each perturbation row needs `perturbation_of: <anchor_id>`
  and `perturbation_type: "medequal"|"medfuzz_*"`. This is a real schema
  change; may need v0.5.

**Acceptance:** paired-row artifacts produced; release manifest counts
perturbation-rows separately from anchor-rows so they don't inflate the
headline `total_item_count`.

## 7. Build key-fact extraction pipeline for open-ended rows

**Track:** Open-ended evaluation · **Priority:** high · **From discussion** + lit review (`docs/open_ended_evaluation_research.md`)

The v0.2 release has 365 rows with `set_type: "open_ended"` (Kenya 308,
AfriMed-SAQ 37, WHB 20) — each has a single reference answer but no
rubrics. Per the literature review, decomposed key-fact recall is the
most defensible automatic scoring approach for this shape.

**To do:**
- Add `prompts/keyfact_extractor/` modular prompt: input is
  `(question, reference_answer)`; output is 3–8 atomic must-cover
  claims.
- Add `src/mamabench/adapters/_keyfact_extraction.py` with the LLM
  call + structured-output validation.
- Add `scripts/extract_keyfacts.py` CLI; uses the same vLLM /
  Qwen3.6-27B-FP8 cluster pipeline as the OBGYN classifier.
- Re-run Kenya / AfriMed-SAQ / WHB adapters to fold `key_facts: list[str]`
  into each row's `source.metadata`.
- Human spot-check ~30 rows for sanity before locking in.

**Acceptance:** every `open_ended` row in v0.2 (or v0.3) carries
`source.metadata.key_facts`; the extraction pipeline + prompt is
reproducible from a clean checkout; results re-runnable on the cluster
in under an hour.

## 9. Reconcile HealthBench filter with spec: ICD-10 codes vs Qwen-classifier categories

**Track:** HealthBench filter · **Priority:** low · **From spec:** `mamabench.md` (Open-ended set)

The spec says HealthBench items should be filtered by **ICD-10 codes**:
pregnancy (Z33.1), obstetric (O-chapter), perinatal (P-chapter). v0.2
instead used our unified Qwen3.6-27B-FP8 OBGYN classifier across the
MATERNAL / NEONATAL / CHILD_HEALTH / SEXUAL_AND_REPRODUCTIVE_HEALTH
categories. Similar intent, different mechanism, **different row set**.

**To do:** decide one of —
- (a) Add ICD-10-based filtering as an alternate / additional metadata
  tag on HealthBench rows; document both filter strategies.
- (b) Switch the HealthBench filter to ICD-10 codes and re-run; document
  the new row set in v0.3 release notes.
- (c) Document the deliberate deviation in the dataset card as "we
  found the LLM classifier broader and more useful than ICD-10
  filtering" and stop here.

**Acceptance:** the choice is documented in the dataset card with an
explicit comparison to spec.

## 10. Refactor mamabench.schema + mamabench.validate for native v0.4 support

**Track:** Code hygiene · **Priority:** medium · **From v0.2 workaround**

`src/mamabench/schema.py` is still pinned at `SCHEMA_VERSION = "0.3"`
and `src/mamabench/validate.py` is hard-coded for v0.3 MCQ-only
invariants. The v0.2 adapters work around this by using
`src/mamabench/adapters/_v0_4_validation.py` for jsonschema-py
validation directly. `mamabench.json` still points at v0.1 / 0.3.

**To do:**
- Bump `SCHEMA_VERSION` to `"0.4"`.
- Replace flat `CANONICAL_FIELDS` with set-type-conditional fields (or
  the minimal common set + per-set-type tuples).
- Extend `CONTROLLED_VOCABULARIES["set_type"]` to
  `{"mcq", "open_ended", "open_ended_rubric"}`.
- Refactor `_validate_item` in `validate.py` to branch on `set_type`:
  - `mcq` keeps existing logic (answer == choices[answer_index], etc.).
  - `open_ended` checks `answer` present + non-empty; choices /
    answer_index forbidden; rubrics forbidden.
  - `open_ended_rubric` checks rubrics present + each rubric has
    `criterion_id` + `points`; sum(max(points, 0)) > 0 invariant;
    answer / choices / answer_index forbidden.
- Update `mamabench.json` pointer to `mamabench_v0.4.schema.json`.
- Update `test_schema.py`, `test_validate.py`, `test_manifest.py`,
  `test_release_manifest.py`, CI runner to match.
- Decide whether `validate_items` continues to accept "0.3" rows for
  v0.1 retro-rebuild compatibility (probably yes; allow either
  version, check fields by set_type and schema_version).

**Acceptance:** all v0.2 adapter scripts switch from
`_v0_4_validation` back to `mamabench.validate.validate_items`;
existing 217 tests pass; `_v0_4_validation.py` is deleted; v0.1
retro-rebuild path still works.
